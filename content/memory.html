LAB 01 / MEMORY ACCESS

Reading a tensor

Follow a warp’s addresses from tensor elements to memory sectors.

Before you start: Some familiarity with arrays and tensor shapes. No CUDA experience or GPU is needed.

START WITH A PYTORCH TENSOR

Where does a tensor keep its numbers?

PyTorch calls the memory holding a tensor’s numbers its storage. A tensor on the CPU normally uses system RAM; a CUDA tensor (on an NVIDIA GPU) normally uses GPU memory, also called VRAM. Here, storage means memory, not a saved file on an SSD or disk.

We often draw a tensor as a grid. In a contiguous, row-major tensor, its values occupy neighbouring positions in memory: all the values of the first row, then the second row, and so on. Each number in this example is FP32 (32-bit floating point), occupying four bytes.

The shape tells PyTorch how to interpret those values as a grid: here it is (2, 4). The strides tell it how many element positions to move when an index changes. Strides (4, 1) mean that moving down one row advances four elements (16 bytes), while moving right one column advances one element (4 bytes).

This tensor has shape (32, 8): 32 rows and eight columns. Its strides (8, 1) mean a move down one row advances 8 elements (32 bytes), and a move right one column advances 1 element (4 bytes).

With arange, the values happen to match their element offsets (positions counted from the beginning of storage). This is a convenient coincidence, not a general property of tensors. Byte offsets are those positions multiplied by four; actual memory addresses are different and are not shown.

Both slices below are views: they share x’s storage. Reading the first row visits neighbouring elements. Reading the first column visits every eighth element. contiguous() copies this strided column into packed storage; that copy also takes work and memory.

Same values. Different addresses.

Interactive draft

Imagine reading one feature from each row of a tensor. The GPU can give a different row to each participating thread.

Each of the 32 threads in a warp can read a different row. When every lane participates, the warp requests 32 values together. Each value here is a 32-bit floating-point number (FP32) occupying four bytes.

The GPU can combine nearby memory requests. Our teaching model groups addresses into aligned 32-byte sectors: bytes 0–31, then 32–63, and so on. Combining nearby requests into fewer memory transactions is called coalescing.

The comparison above shows the key result: reading 32 adjacent values touches 4 sectors; reading every 8th value touches 32 sectors, even though both request the same 128 bytes of useful data. Use the experiment below to explore how stride, offset, and active lanes change the sector count.

What this model tells you

We count distinct aligned 32-byte sectors touched by one warp’s global-memory load, with four-byte aligned FP32 values and a sector-aligned base pointer. This matches the coalescing accounting described for devices of compute capability 6.0 or newer in NVIDIA’s CUDA Best Practices Guide.

These counts are not DRAM transactions or elapsed time. Caches, reuse between warps, stores, instruction issue, and memory-controller behaviour are outside this model. A sector diagram does not show execution order. More sectors can increase memory traffic; it does not imply a proportional slowdown.

Make a prediction you can explain.

  2. Switch to Contiguous. Now it reads neighbouring features. Compare requested bytes and sector coverage. Which changed?

Explain the result in your own words, then compare

Each sector holds eight FP32 values. Neighbouring lanes can use different values in the same sector. With a stride of eight elements, each lane reaches a different sector. Shifting a consecutive range by one element can make it cross an extra sector boundary.

In an AI workload, changing how threads map onto tensor dimensions can change this access pattern. A transpose or a different tensor layout may help one operation and add costs elsewhere. Count the work across the whole operation before choosing a layout.
